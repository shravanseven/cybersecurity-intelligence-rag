# Cybersecurity Intelligence RAG System

## Project Specification, Architecture & Development Plan

**Project Type:** Personal portfolio / learning project
**Primary Domain:** Cybersecurity Intelligence + Retrieval-Augmented Generation
**Primary Goal:** Build a real, evaluated RAG system that can retrieve, connect, and explain cybersecurity intelligence from multiple authoritative sources.

---

# 1. Project Vision

The project is a **Cybersecurity Intelligence RAG System** that allows a user to ask natural-language questions about vulnerabilities, affected products, exploitation status, mitigations, and related cybersecurity information.

The system will retrieve relevant evidence from multiple cybersecurity sources and use a locally hosted LLM to produce a **grounded, citation-backed answer**.

The core philosophy is:

> **Sources are the source of truth. The LLM is the reasoning and explanation layer.**

The LLM should not be trusted to independently know whether a vulnerability exists, which products are affected, or what the current mitigation is.

Instead:

```text
Cybersecurity Sources
        ↓
Data Ingestion
        ↓
Normalization
        ↓
Chunking / Structuring
        ↓
Embeddings
        ↓
ChromaDB
        ↓
Retrieval
        ↓
Relevant Evidence
        ↓
Ollama LLM
        ↓
Grounded Answer + Citations
```

The project will then evolve this baseline through experiments and evaluation.

---

# 2. Problem Statement

Cybersecurity information is fragmented across different sources.

A single vulnerability may have:

* a CVE record
* severity information
* affected products
* CWE information
* vendor advisories
* remediation guidance
* exploitation information
* inclusion in CISA's KEV catalog
* references to additional security research

A security analyst therefore often needs to consult multiple sources to answer a seemingly simple question.

For example:

> "What is CVE-X, which products are affected, is it known to be exploited, and what mitigation is recommended?"

The objective of this project is to create a system that can retrieve the relevant evidence from these sources and synthesize it into one understandable answer.

---

# 3. What This Project Is NOT

This distinction is important because it prevents scope explosion.

The project is **not**:

* a complete SIEM
* an intrusion detection system
* a vulnerability scanner
* an automated penetration-testing tool
* an exploit-generation system
* a commercial threat-intelligence platform
* a fully autonomous security agent
* a replacement for professional security analysts

It is primarily a:

> **Cybersecurity information retrieval, synthesis, and question-answering system.**

---

# 4. Intelligence Sources

The initial system will work with three major categories.

## 4.1 CVE / Vulnerability Records

Primary source:

**NVD — National Vulnerability Database**

NVD provides structured vulnerability information including CVE identifiers, descriptions, references, CVSS information, CWE information, and affected software/configuration information. Its current documentation identifies the 2.0 APIs as the preferred API approach.

Example conceptual record:

```text
CVE ID
Description
Published Date
Last Modified
CVSS
CWE
Affected Products
References
```

This information is highly structured.

---

## 4.2 Known Exploited Vulnerabilities

Primary source:

**CISA Known Exploited Vulnerabilities (KEV) Catalog**

The KEV catalog is particularly useful because it provides information about vulnerabilities that CISA identifies as having evidence of exploitation.

This introduces an important intelligence dimension:

```text
CVE exists
        ↓
CVE has severity
        ↓
CVE may affect product X
        ↓
CVE may also be known to be exploited
```

This allows the system to answer questions that go beyond simply retrieving a CVE description.

---

## 4.3 Security Advisories

The system will also ingest security advisories from authoritative vendors or security organizations.

These are important because they contain information that structured CVE records may not fully capture:

* affected versions
* vendor-specific impact
* remediation
* workarounds
* upgrade recommendations
* product-specific context
* additional technical explanation

These documents will typically contain considerably more natural language than CVE records.

---

# 5. Why Three Data Types?

We are intentionally **not creating three independent RAG systems**.

Instead, the architecture will have a common ingestion and retrieval pipeline.

Conceptually:

```text
                ┌── CVE Records
                │
Sources ────────┼── KEV Records
                │
                └── Security Advisories
                        ↓
                Normalization Layer
                        ↓
                Common Internal Model
                        ↓
             Structured + Textual Data
                        ↓
                  Retrieval Layer
```

The complexity comes from the differences between the sources.

For example:

### CVE

Highly structured.

```json
{
  "cve_id": "...",
  "description": "...",
  "cvss": 9.8,
  "published": "...",
  "references": [...]
}
```

### Advisory

More narrative.

```text
Vendor Security Advisory

A vulnerability was discovered in...

Affected versions:
...

Customers should upgrade to...
```

### KEV

Structured intelligence about exploitation.

```text
CVE ID
Vendor
Product
Date Added
Due Date
Required Action
```

The project will therefore learn an important RAG engineering lesson:

> **Not every piece of information should be represented or retrieved in exactly the same way.**

# 6. Core Use Cases

The system should eventually support the following categories.

## 6.1 Vulnerability Lookup

Example:

> What is CVE-XXXX-XXXX?

Expected answer:

* vulnerability description
* severity
* affected products
* relevant evidence
* sources

---

## 6.2 Affected Product Queries

Example:

> Which versions of Product X are affected by CVE-XXXX?

The answer should rely on structured vulnerability information where possible.

---

## 6.3 Mitigation Queries

Example:

> What mitigation is recommended for CVE-XXXX?

The system should prioritize advisory/remediation information rather than hallucinating a generic recommendation.

---

## 6.4 Exploitation Status

Example:

> Is CVE-XXXX known to be exploited?

The system should determine whether the vulnerability appears in the KEV data.

---

## 6.5 Cross-Source Questions

Example:

> What does the vendor recommend for CVE-X and is it listed in the KEV catalog?

This is an important capability because the answer requires combining multiple sources.

---

## 6.6 Analytical Queries

Example:

> Show me critical vulnerabilities affecting Product X that are also known to be exploited.

This is where structured filtering becomes important.

The system should eventually be able to combine:

```text
Product = X
AND
Severity = Critical
AND
KEV = True
```

rather than trying to solve everything through semantic similarity.

---

## 6.7 Comparison

Example:

> Compare CVE-X and CVE-Y in terms of severity, affected products and exploitation status.

This requires retrieving multiple pieces of evidence.

---

## 6.8 Insufficient-Evidence Questions

Example:

> Which threat actor definitely exploited CVE-X?

If the indexed sources do not establish this, the system should say that sufficient evidence was not found.

This is an important part of the project.

The goal is not:

> "Always generate an answer."

The goal is:

> **"Generate an answer when sufficient evidence exists."**

---

# 8. RAG Pipeline

The complete pipeline will eventually be:

```text
              DATA INGESTION
                    ↓
             SOURCE PARSING
                    ↓
             NORMALIZATION
                    ↓
           STRUCTURED STORAGE
                    +
              TEXT CREATION
                    ↓
               CHUNKING
                    ↓
              EMBEDDINGS
                    ↓
               CHROMADB
                    ↓
          ┌───────────────────┐
          │      QUERY        │
          └─────────┬─────────┘
                    ↓
             QUERY EMBEDDING
                    ↓
              RETRIEVAL
                    ↓
           OPTIONAL FILTERING
                    ↓
             OPTIONAL KEYWORD
                    ↓
              RERANKING
                    ↓
              TOP CONTEXT
                    ↓
               OLLAMA
                    ↓
           GROUNDED ANSWER
                    ↓
              CITATIONS
```

But the components after basic retrieval will be introduced incrementally.

# 9. Retrieval Evolution

This is one of the most important parts of the project.

We will deliberately evolve retrieval instead of implementing everything immediately.

## V1 — Dense Retrieval

```text
Query
 ↓
Embedding
 ↓
ChromaDB
 ↓
Top-K
```

This establishes the baseline.

---

## V2 — Metadata Filtering

Introduce metadata such as:

```text
source_type
source_name
cve_id
vendor
product
published_date
severity
kev_status
```

Now the system can perform queries such as:

```text
source_type = "KEV"
```

or:

```text
severity = "CRITICAL"
```

---

## V3 — Hybrid Retrieval

Combine:

```text
Semantic Search
      +
Keyword Search
```

Why?

Semantic search understands meaning.

Keyword search is extremely useful for exact identifiers.

For example:

```text
CVE-2025-12345
```

is fundamentally different from:

```text
How is this vulnerability exploited?
```

An exact CVE identifier is often better handled through keyword/metadata lookup.

---

## V4 — Reranking

Initial retrieval may produce:

```text
Top 10 results
```

A reranker can examine those results more carefully and reorder them.

```text
Query
 ↓
Initial Retrieval
 ↓
Top 20
 ↓
Reranker
 ↓
Best 5
```

This will only be introduced if evaluation demonstrates that initial retrieval is insufficient.

---

# 10. Important Architectural Principle

One of the project's central lessons will be:

> **Do not use vector search for every problem.**

For example:

### Query

> "What are the critical CVEs affecting Product X in 2025?"

Potential approach:

```text
Structured filtering
```

### Query

> "How can this vulnerability be exploited?"

Potential approach:

```text
Semantic retrieval
```

### Query

> "Is CVE-X in the KEV catalog?"

Potential approach:

```text
Exact identifier + structured lookup
```

The final architecture should therefore become a **retrieval system**, not merely a vector database wrapped around an LLM.

## 11.2 Text Representation

Used for information such as:

```text
Impact explanation

```

This information is suitable for semantic retrieval.

# 12. Common Internal Document Model

Different sources should be normalized into a common internal representation.

Conceptually:

```text
Document
│
├── document_id
├── source_type
├── source_name
├── title
├── cve_id
├── vendor
├── product
├── published_date
├── modified_date
├── severity
├── kev_status
├── url
├── content
└── metadata
```

Not every source will populate every field.

For example:

```text
CVE record
    cve_id = CVE-X
    severity = CRITICAL
    source_type = cve

KEV record
    cve_id = CVE-X
    kev_status = true
    source_type = kev

Vendor advisory
    cve_id = CVE-X
    source_type = advisory
    content = long textual advisory
```

This allows the system to recognize that these are different representations of the same vulnerability.

---

# 13. Entity Linking

An important future capability is recognizing relationships.

For example:

```text
CVE-2025-XXXX
      │
      ├── NVD record
      │
      ├── Vendor advisory
      │
      └── CISA KEV record
```

The common identifier:

```text
CVE-2025-XXXX
```

acts as an entity key.

This is extremely useful because a vulnerability may appear in multiple sources.

---

# 14. Deduplication

The same vulnerability may appear in:

* NVD
* vendor advisory
* KEV
* other security sources

We should not blindly embed identical information multiple times.

The ingestion pipeline will therefore eventually need to answer:

> Is this new information, or another representation of something already stored?

Possible identifiers:

```text
CVE ID
source
document URL
content hash
```

Deduplication will initially remain simple.

We do not need a sophisticated entity-resolution system on day one.

---

# 15. Chunking Strategy

Chunking will be treated as an experiment rather than a fixed assumption.

Initial baseline:

```text
fixed-size chunks
+
small overlap
```

For example:

```text
Chunk size: experiment-dependent
Overlap: experiment-dependent
```

We will not assume that one chunk size is optimal.

Later experiments can compare:

```text
Small chunks
vs
Medium chunks
vs
Large chunks
```

and investigate:

* retrieval quality
* answer quality
* context size
* latency
* irrelevant information

---

# 16. Embeddings

The system will use an embedding model locally where practical.

The embedding model will be treated as an experimental component.

We will record:

```text
Model
Embedding dimension
Latency
Retrieval quality
Resource requirements
```

The first objective is not to find the "best embedding model in the world."

It is to establish a reproducible baseline.

# 17. Vector Database

## Chosen Technology: ChromaDB

ChromaDB will be used for the initial vector store.

The reason is primarily learning and project simplicity.

It gives us:

* local development
* straightforward vector storage
* metadata support
* similarity search
* easy experimentation
* low infrastructure overhead

Alternatives considered:

### FAISS

Advantages:

* mature vector similarity library
* excellent performance
* widely used

Disadvantages for this project:

* more infrastructure must be built around it
* metadata handling is less convenient as the primary application store

### Qdrant

Advantages:

* powerful metadata filtering
* production-oriented
* strong vector database capabilities

Disadvantage:

* more infrastructure than necessary for the first version

### pgvector

Advantages:

* PostgreSQL integration
* useful production architecture

Disadvantage:

* introduces a database infrastructure dependency before it is necessary

### Decision

Start with:

```text
ChromaDB
```

Later, if project requirements demonstrate a need for something else, we can compare alternatives experimentally.

# 18. LLM

## Chosen Approach: Ollama

The LLM layer will initially run locally through Ollama.

Conceptually:

```text
Application
     ↓
Ollama
     ↓
Local LLM
```

Benefits:

* no mandatory external API
* local experimentation
* reproducibility
* privacy
* easier experimentation with different models

The specific model should not be hard-coded into the architecture.

It should be configurable.

For example:

```text
OLLAMA_MODEL=...
```

This allows the model to be changed without redesigning the application.

---

# 19. Why We Are Not Starting With LangChain

The first version should implement the RAG pipeline directly.

Conceptually:

```python
query
   ↓
embed(query)
   ↓
chromadb.search()
   ↓
build_context()
   ↓
ollama.generate()
```

This is intentional.

The objective is to understand:

* embeddings
* retrieval
* metadata
* context construction
* prompting
* citations
* evaluation
* latency

before introducing an abstraction layer.

Later, a framework can be introduced if there is a concrete reason.

# 20. Prompting Strategy

The LLM will receive something conceptually like:

```text
SYSTEM:

You are a cybersecurity intelligence assistant.

Answer only using the supplied evidence.

If the evidence is insufficient, say that sufficient
evidence was not found.

Do not invent facts.

Cite the sources supporting your answer.

CONTEXT:

[Source 1]
...

[Source 2]
...

USER QUESTION:

...
```

The important principle is:

> Retrieval determines what evidence the model gets; prompting determines how the model uses that evidence.

---

# 21. Citation System

Citations are a core feature, not decoration.

Every answer should be traceable to retrieved evidence.

Example conceptual response:

```text
CVE-XXXX is a critical vulnerability affecting ...

The vulnerability affects ...

CISA lists the vulnerability in its Known Exploited
Vulnerabilities catalog.

Sources:
[1] NVD
[2] Vendor Advisory
[3] CISA KEV
```

Each source should eventually contain:

```text
source name
title
URL
document identifier
```

The user should be able to click the source.

---

# 22. Groundedness

The project will explicitly distinguish:

### Model knowledge

Information the LLM already learned during training.

### Retrieved evidence

Information supplied by our system.

### Grounded answer

An answer supported by the retrieved evidence.

Example:

```text
Retrieved evidence:
"Version 4.2 is affected."

Answer:
"Version 4.2 is affected."
```

This is grounded.

If the model instead says:

```text
"Version 4.2 and 4.3 are affected"
```

when the retrieved evidence only mentions 4.2, the additional claim is unsupported.

The evaluation system should detect these failures.

---

# 23. Evaluation System

Evaluation will be a first-class component.

It will not be something we add at the very end.

The evaluation harness will behave like a test suite for the RAG system.

Conceptually:

```text
Evaluation Dataset
       ↓
Run RAG System
       ↓
Collect Results
       ↓
Calculate Metrics
       ↓
Analyze Failures
       ↓
Make Architecture Decision
       ↓
Change System
       ↓
Run Evaluation Again
```

# 24. Evaluation Dataset

Initial target:

**30–50 carefully designed questions**

The dataset should include categories such as:

### Category A — Direct Retrieval

> What is CVE-X?

### Category B — Metadata

> What is the CVSS score?

### Category C — Product

> Which products are affected?

### Category D — KEV

> Is this vulnerability known to be exploited?

### Category E — Multi-source

> Compare the vendor advisory with the KEV information.

### Category F — Multi-document

> Summarize the vulnerability using NVD and the vendor advisory.

### Category G — Comparison

> Compare CVE-X and CVE-Y.

### Category H — Unanswerable

> Which threat actor exploited this vulnerability?

when the indexed sources do not establish that fact.

# 25. Evaluation Metrics

The project will initially track several dimensions.

## Retrieval

### Recall@K

Did the system retrieve the relevant evidence within the top K results?

---

### Precision@K

How many of the retrieved results were actually relevant?

---

### MRR

Mean Reciprocal Rank.

Useful for determining how high the first relevant result appears.

---

## Answer

### Correctness

Does the answer correctly answer the question?

### Groundedness / Faithfulness

Are the claims supported by retrieved evidence?

### Relevance

Does the answer actually address the user's question?

---

## System

### Latency

Measure:

```text
embedding time
retrieval time
LLM generation time
total response time
```

This gives the project an engineering dimension rather than only an AI dimension.

---

Explicitly deferred:

# 38. Features Explicitly Deferred

### No automated threat hunting

Not the goal.

### No real-time enterprise feeds

Initial ingestion will use public sources.

### No mobile application

Not relevant.

### No elaborate frontend

Keep the UI simple.

# 40. Data Freshness

Because cybersecurity information changes over time, freshness is important.

NVD provides APIs and feeds intended for keeping vulnerability information current; its current documentation recommends the 2.0 APIs and provides recent/modified feeds for synchronization.

The ingestion architecture should therefore eventually support:

```text
Initial ingestion
       ↓
Store source state
       ↓
Track last update
       ↓
Fetch new/modified records
       ↓
Update index
```

But Version 1 does not need a sophisticated scheduler.

First make ingestion work.

Then automate it.

---

# 41. Data Pipeline

The ingestion process should eventually look like:

```text
Source
 ↓
Downloader / API Client
 ↓
Raw Data
 ↓
Parser
 ↓
Normalizer
 ↓
Validation
 ↓
Deduplication
 ↓
Structured Metadata
 +
Text
 ↓
Chunking
 ↓
Embedding
 ↓
ChromaDB
```

Raw data should ideally be preserved separately from processed data.

This gives us reproducibility.

---

# 42. Why Preserve Raw Data?

Suppose we discover that our parser was wrong.

Without raw data:

```text
Source
 ↓
Parser
 ↓
Database
```

we may need to download everything again.

With raw data:

```text
Raw Source
     ↓
Parser v1
     ↓
Processed Data

Raw Source
     ↓
Parser v2
     ↓
Processed Data v2
```

This also makes experiments reproducible.

# 65. Project Development Philosophy

The project will follow five rules.

### Rule 1 — Build before abstracting

Understand the underlying RAG pipeline before introducing large frameworks.

### Rule 2 — Measure before optimizing

Do not add sophisticated retrieval techniques without evidence that they are needed.

### Rule 3 — Prefer authoritative evidence

The system should prioritize reliable cybersecurity sources.

### Rule 4 — Keep scope controlled

A smaller, deeply engineered RAG system is preferable to a huge collection of half-implemented features.

### Rule 5 — Let GitHub tell the story

The repository should show the actual progression:

```text
Question
 ↓
Implementation
 ↓
Failure
 ↓
Experiment
 ↓
Decision
 ↓
Improvement
```

That progression is part of the project.

# 66. Final Project Identity

The simplest description of the finished project is:

> **A cybersecurity intelligence RAG system that retrieves and synthesizes vulnerability information from multiple authoritative sources, produces grounded answers using a locally hosted LLM, provides source citations, and uses systematic evaluation to improve its retrieval architecture.**

The deeper description is:

> **An experiment-driven RAG engineering project exploring how structured cybersecurity intelligence and unstructured security advisories can be combined into a grounded question-answering system, with retrieval quality, answer groundedness, latency, and architectural tradeoffs evaluated throughout development.**

That second description is what the project should ultimately communicate on GitHub and in technical discussions.
